# Blind evaluation tooling

After listeners download their existing review-page JSON, run:

`python3 -m mixlab.evaluation /private/pack /private/ratings/listener-*.json`

Aggregation verifies the pack identity against the private answer key and render hashes, re-hashes all listening files, requires complete coverage, rejects repeated reviewers (case-insensitive), duplicate/foreign trials and foreign pack IDs. Ties and both-unusable votes have explicit counts and are excluded from decisive preference denominators. Counts are grouped by pair **and candidate family**, avoiding misleading pooling across alternatives. Integrated loudness (BS.1770-4) is re-measured from the bound audio per trial; a difference above 0.5 LU, undefined loudness, near-full-scale samples or mostly silent windows are reported as `audio_confounds`. Packs from `benchmark` are loudness-matched per pair before freezing; see [loudness-matching ADR](adr/loudness-matching.md).

The existing four-family pack is exploratory: comparing three candidates per pair is not the frozen one-candidate pilot in architecture.md. No output automatically passes M1, and synthetic votes remain software tests. Before a pilot: select one candidate per pair without seeing evaluation responses, use real partitioned permitted audio, confirm `audio_confounds` is empty, collect at least three distinct real listeners, record audible defects and perform independent review. The CLI cannot verify that three pseudonyms are three people.

Do not publish source audio, private answer keys, raw reviewer identities or source paths. Share only the neutral review directory with authorized listeners. No listener data has been collected in this implementation.

## Freezing the pilot study (before any ratings)

Build the candidate file from the private library instead of by hand: `python3 -m mixlab.evaluation.candidates /private/library/library.json /private/study/split.json /private/study/candidates.json [--manual-keys /private/study/keys.json] [--measure-keys]`. The split file `{"schema_version": 1, "development": [...], "evaluation": [...]}` must assign every manifest track exactly once, and decide it before any listening. SHA-256, BPM and permission declarations come from the validated manifest. Manual keys (`{"schema_version": 1, "keys": {"track-id": "A minor"}}`) are labelled `manual` and always win. `--measure-keys` fills the rest with ChromaKeyProvider proposals labelled `measured-heuristic`, and an abstention stays `unavailable`. The output is written exclusively and never overwritten.

`python3 -m mixlab.evaluation.study freeze /private/study/candidates.json /private/study/study.json --pairs 8` selects 5–10 pairs from tracks declared `"split": "evaluation"` only. Candidate schema v1: `{"schema_version": 1, "tracks": [{"id", "sha256", "bpm", "key", "key_source", "split", "rights"}]}`. `key_source` is `manual`, `measured-heuristic` or `unavailable` (then `key` is null); a recording hash may appear only once. Selection is seeded hash order (the seed is drawn and recorded when omitted), stratified half harmonically compatible (Camelot distance ≤ 1) and half contrasting/unknown. That keeps the study representative rather than flattering. Each track is used at most twice by default. Pairs need equal BPM unless `--tempo-tolerance-percent` is set, and those pairs are labelled `renderable_without_stretch: false`, because the current renderer does not time-stretch. Each pair gets exactly one preselected candidate family, balanced across `bass_swap`, `echo_exit` and `hard_cut`, for comparison with the equal-power baseline. The study manifest records the candidate-file hash, a hash of the development track IDs and a `study_id` over all content. It is written exclusively (never overwritten). `verify` recomputes the identity and re-checks reuse and family balance.

Frozen A/B packs now attenuate both candidate and baseline to the quieter integrated BS.1770-4 loudness before publication; the pack identity is derived from the exact matched listening WAV bytes, while private render evidence also preserves the unmatched render hashes. Silent and sub-400 ms audio cannot be matched and fail closed without publishing a partial pack. Short-term loudness, true peaks and human musical preference remain unverified.

The frozen study is a selection, not a result. Rendering and pack generation from it, loudness matching, and at least three real listeners remain required before any preference claim. Measured-heuristic keys must be confirmed by a human before the study is used.

After freezing, align exactly the frozen pairs in the private library manifest (start offsets, beats, BPM; at most 10 pairs) and render: `python3 -m mixlab.evaluation.study_pack /private/library/library.json /private/study/study.json /private/pack-pilot`. It verifies the study, refuses pairs that lack a verified alignment, whose source hash differs from the frozen one, or that need time-stretching. It then renders only the baseline and the one preselected family per pair, giving one trial per pair. The pack is built in a private `.mixlab-staging-*` directory beside the destination, checked with `verify_pack`, and only then renamed into place. A failed render removes the staging directory, so no partial `review/` ever exists. CLI errors from the OS are reduced to a constant "details withheld" message so private paths are never echoed. The pack layout, public receipt fields and `pack_id` are exactly those of `mixlab benchmark`, so the ML-07 review preflight (`inspect_review_pack(..., require_receipt=True)`) and `python3 -m mixlab.evaluation` accept it unchanged. Only private evidence records `study_id`, and that string alone proves nothing because it can be edited. Before listeners get the pack, check it against the independently pinned study file with `mixlab.evaluation.study_pack.verify_study_pack(pack, study)`. That re-derives the binding from the verified study: same pair order, same source recording hashes, only baseline versus the preselected family in each trial, and exactly two renders per frozen pair with no other render groups. This is a consistency check, not a signature. A/B positions come from a schedule fixed before rendering. Baseline-as-A is balanced overall and within each candidate family (difference at most 1), and no side repeats more than twice in a row, so a valid pack cannot put the baseline on one side in every trial. Omit `--seed` for real listeners.
